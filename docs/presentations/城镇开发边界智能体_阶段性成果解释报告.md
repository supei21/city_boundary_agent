# 城镇开发边界地块识别智能体阶段性成果解释报告

**报告主题：** 基于已有论文方法的智能决策工作流构建与 Demo 验证  
**研究对象：** 武汉市街区属性记录与城镇开发边界调整候选识别  
**报告时间：** 2026 年 8 月

> **报告定位：** 本报告用于书面说明当前阶段的研究思路、智能体框架、原型实现、验证结果和后续计划。现阶段成果主要用于验证技术路线与工具调用流程，不代表正式的城镇开发边界规划结论。

## 摘要

本阶段研究以城镇开发边界识别、适宜性评价和增量空间调整相关论文为方法基础，尝试将传统的指标评价、机器学习预测、可解释性分析与规划约束检查，重构为一套可以由大模型自主编排的智能体工作流。

在该框架中，大模型主要承担用户意图理解、任务规划、工具选择和结果组织；适宜性评分、硬约束校验及候选地块分类则由具有明确输入输出的业务工具执行。通过这种职责分离，可以降低大模型直接参与数值计算和规划判断时可能产生的数据编造、结论漂移和结果不可复现问题。

目前已经完成一个对话式最小原型。该原型读取已经整理好的街区 JSON 或 CSV 属性记录，支持查看街区、读取指定街区属性、分析指定街区以及识别调入或调出候选地块。系统采用 ReAct 智能体进行工具选择，并保留确定性规则工作流作为业务执行层和离线兜底机制。当前 Demo 配置了 3 条典型示例街区、4 类智能体工具和 12 项自动化测试，已验证基本技术链能够运行，但尚未训练正式 XGBoost 模型、生成真实 SHAP 解释或接入 GIS 空间约束分析。

**关键词：** 城镇开发边界；智能体；LangChain；ReAct；XGBoost；SHAP；规划约束；可解释决策

## 一、基于已有论文方法构建智能体总体框架

### 1.1 已有研究提供的方法基础

前期收集的论文为城镇开发边界识别提供了较为清晰的方法链条。

首先，通过人口、产业、交通、公共服务、地形、土地利用和开发强度等指标，刻画地块或街区的开发条件，并形成多维度适宜性评价体系。

其次，利用 XGBoost 等机器学习方法学习多源指标与开发适宜性之间的非线性关系，使系统能够根据街区属性预测开发适宜性概率或等级。

再次，通过 SHAP 对模型进行全局和局部解释。全局解释用于识别影响总体预测的关键指标，局部解释用于说明单个街区获得某一预测结果的具体原因，从而提高模型结果的可理解性和可审查性。

最后，将生态保护红线、永久基本农田、灾害风险、现有开发边界等规划条件作为硬约束参与候选识别。即使某个街区具有较高适宜性，只要涉及不可突破的规划约束，也不能直接识别为优先调入地块。

传统研究通常按照数据处理、模型训练、结果解释和规划判断的线性过程组织。该方式适合单次分析，但在面对规划人员的自然语言任务、多轮交互和不同分析需求时，仍需要人工选择分析步骤、组织输入参数和解释结果。因此，本研究进一步考虑如何将论文中的方法链重构为可由智能体动态编排的工作流。

### 1.2 从算法流程到智能体工作流

智能体总体框架的构建主要包括三个层次。

**第一，论文方法抽象。** 将指标体系、XGBoost 预测、SHAP 解释和规划约束视为相互独立的业务能力。每项能力都应具有明确的输入字段、输出结果、异常状态和质量检查规则，而不是全部写入一个固定脚本。

**第二，智能体能力重构。** 设置总控智能体负责需求理解、任务拆解、工具选择和状态管理，同时配置规划知识解析、数据检查、训练管理、报告审查等职责模块。总控智能体根据用户问题决定需要调用哪些工具以及工具之间的执行顺序。

**第三，规划决策闭环。** 在模型预测之后继续执行空间约束校验和候选类型判定，并通过人工审核、规则修正和经验反馈形成可持续迭代的决策闭环。

PPT 第 1 页展示的是完整目标架构，包括输入与任务层、智能编排与知识理解层、空间分析与模型工具层、核心识别与决策层、成果输出层以及人机协同反馈层。当前 Demo 仅实现其中的自然语言交互、总控工具选择、街区属性查询、规则识别和结果解释等最小闭环。XGBoost、SHAP、GIS 空间分析、知识库和模型注册等能力将在后续阶段逐步接入。

## 二、研究任务、核心问题与阶段实施边界

### 2.1 核心研究问题

本研究需要解决的核心问题是：面对多个街区、多源指标和复杂规划约束，如何让大模型不仅能够生成说明文字，还能够准确识别规划人员的任务意图，自主选择合适的分析工具，并依据结构化证据形成可追溯的调入、调出、保持或人工复核建议。

### 2.2 智能决策的基本环节

智能体的决策过程被划分为四个基本环节。

**意图理解。** 系统首先判断用户希望查看数据、分析指定街区、比较多个街区、筛选调入候选，还是筛选建议调出街区。

**工具选择。** 系统根据任务类型决定调用街区目录、属性读取、指定街区分析或批量候选识别工具。当用户没有提供明确的 `block_id` 时，智能体应先查询街区目录，而不能自行编造分析对象。

**规则推理。** 工具负责执行数据校验、适宜性评分、规划约束检查、候选分类和一致性审查，并返回结构化结果。

**结果解释。** 大模型根据工具结果组织中文回答，说明结论、主要依据、风险、缺失信息和置信度，但不得擅自修改规则结论、分数和硬约束状态。

### 2.3 当前阶段的实施边界

当前阶段只读取已经整理好的街区属性记录，不直接处理 Shapefile、栅格或地理数据库，也不调用 ArcPy。人口、土地利用等尚未完全确认语义的字段按缺失或待确认处理，避免智能体自行假定其含义。

当前适宜性结果主要由配置化规则生成，用于验证交互、工具路由和结果结构。因此，现阶段可以评价智能体是否能够理解任务并调用正确工具，但不能据此评价城镇开发边界识别的正式规划精度。

## 三、当前原型的数据—规则—交互闭环

### 3.1 输入数据与典型示例

原型支持 JSON 和 CSV 两种街区属性输入方式。分析时要求每条记录至少包含唯一的 `block_id` 和是否位于现有开发边界内的标识。其他指标可以包括街区面积、中心点经纬度、POI 密度及分类数量、DEM 均值和起伏度、人口及人口密度、道路密度、主要土地利用类型，以及灾害、生态红线和基本农田约束。

当前内置 3 条典型示例记录，分别用于模拟边界外高适宜街区、涉及生态硬约束的边界外街区，以及边界内高风险低适宜街区。这些记录主要用于覆盖不同规则分支，不属于正式模型训练样本。

### 3.2 确定性规则工作流

规则工作流依次执行输入校验、适宜性评价、规划约束检查、候选类型判定、结果审查和报告汇总。所有权重、尺度和阈值存放在 YAML 配置文件中，避免将关键判断直接写入提示词。

当前候选分类规则包括一级优先调入、二级优先调入、建议调出、保持现状和人工复核。硬约束不能被较高的适宜性分数抵消，缺失的 DEM、人口或土地利用信息不得自动填 0。规则工作流还会检查结论是否与评分一致、是否绕过硬约束，以及是否需要转入人工复核。

### 3.3 当前工具与自动化验证

当前工具箱包含以下 4 类工具。

| 工具名称 | 主要功能 | 典型输出 |
|---|---|---|
| `list_blocks` | 列出可用街区，可按边界内外筛选 | `block_id`、名称、边界状态 |
| `get_block_details` | 读取指定街区原始属性，不运行规划分析 | 街区属性记录、未找到的ID |
| `analyze_blocks` | 对指定街区运行评分、约束和候选分类 | 分类、分数、证据、风险 |
| `identify_candidate_blocks` | 分析全部街区并筛选调入或调出候选 | 候选清单与分类汇总 |

截至当前版本，原有业务规则与新增工具共通过 12 项自动化测试。测试内容覆盖单街区分析、街区属性查看、调入候选筛选、调出识别、比较任务、硬约束处理、结果数量检查以及 JSON 序列化等。

## 四、大模型自主选择工具的核心技术架构

### 4.1 大模型与业务工具的职责分离

当前原型采用 ReAct 式智能体结构。大模型负责读取用户问题、判断任务类型、决定是否调用工具以及组织最终回答；街区查询、适宜性评分、约束判断和候选分类则由工具和确定性工作流执行。

这一设计可以概括为“大模型负责选择，工具负责计算”。大模型的语言理解能力被用于自然语言交互和任务编排，可重复、可审计的计算则保留在业务程序中。

系统提示词明确限制智能体不得编造 `block_id`、属性、分数和规划结论。用户没有指定明确街区时，智能体应先调用街区目录工具；用户只要求查看原始属性时，不应运行规划分析；用户要求筛选调入或调出候选时，则调用批量候选识别工具。

### 4.2 可扩展工具接口

现有工具箱采用统一输入输出方式，后续可以继续加入 XGBoost 预测、SHAP 解释和 GIS 空间分析工具。

XGBoost 工具负责读取街区指标并输出适宜性概率或等级；SHAP 工具负责输出全局指标重要性和单街区指标贡献；GIS 工具负责执行开发边界、生态红线、永久基本农田和灾害风险等空间叠加。

由于对话界面、智能体编排和业务工具之间已经解耦，新增工具后不需要整体重写用户交互流程。智能体只需要获得新增工具的名称、功能说明、输入要求和返回格式，即可根据用户意图决定是否调用。

需要强调的是，大模型不能直接改写预测结果、阈值和硬约束。若工具执行失败、数据不足或规则冲突，系统应返回风险提示并转入人工复核，而不是自行补全缺失证据。

## 五、Demo 成果与典型交互过程

### 5.1 对话式界面

当前 Demo 采用 Streamlit 构建对话界面。用户可以在侧边栏选择内置示例，也可以上传 JSON 或 CSV 格式的街区数据，并查看模型启用状态和已加载街区数量。

主界面提供自然语言输入、街区数据表、识别结果表、JSON 下载和智能体解析过程展示。用户可以提出“查看全部街区数据”“分析某个街区”“比较两个街区”“哪些街区适合调入开发边界”等问题。

### 5.2 典型任务执行过程

以用户提出“哪些街区适合调入开发边界”为例，智能体首先识别这是一个面向全部街区的调入候选筛选任务，然后调用 `identify_candidate_blocks` 工具。

该工具对当前全部街区执行数据检查、适宜性评价和规划约束判断，并仅保留一级优先调入或二级优先调入结果。最终回答包括街区编号、适宜性分数、约束状态、主要依据、风险和缺失信息。

界面中的“查看智能体解析过程”用于展示智能体选择的工具和目标街区，便于检查模型是否正确理解用户任务。如果大模型接口不可用，系统将回退到本地关键词解析和规则模板，使 Demo 仍可运行。但本地回退路径主要用于保证演示稳定性，不等同于完整的大模型工具调用能力。

### 5.3 Demo 的实际作用

当前 Demo 的作用不是替代正式GIS分析，也不是直接给出法定规划调整结论，而是验证以下问题：大模型能否理解规划人员的自然语言请求；能否根据请求自主选择正确工具；能否基于工具返回的数据组织可追溯回答；当数据不足或出现硬约束时，能否主动提示风险并转入人工复核。

## 六、阶段结论、现存不足与下一阶段计划

### 6.1 已完成的阶段成果

本阶段已经完成对话式街区识别 Demo、ReAct 智能体工具选择流程、4 类街区工具、确定性规则工作流、模型配置入口、异常回退机制和自动化测试。

总体上已经证明“自然语言请求—工具选择—规则分析—结构化解释”这一技术链可以运行，并为后续模型和 GIS 能力接入保留了明确接口。现阶段成果的主要价值是建立了可控、可解释和可扩展的智能体软件骨架。

### 6.2 现存不足

当前内置数据只有 3 条示例记录，无法用于评估真实预测精度；适宜性评价仍以配置化规则为主，尚未训练正式 XGBoost 模型；系统尚未生成真实 SHAP 全局和局部解释；生态红线、永久基本农田、灾害风险和开发边界等约束尚未通过 GIS 空间叠加计算；人口栅格和土地利用分类等部分指标语义仍需进一步确认。

因此，当前成果证明的是智能体框架和软件流程的可行性，而不是规划识别结果的准确性。正式研究需要使用真实样本、明确训练标签、建立规范的评价指标，并通过对比实验和专家审查验证系统结论。

### 6.3 下一阶段研究计划

| 阶段 | 主要任务 | 预期产出 |
|---|---|---|
| 数据准备 | 补充真实街区样本与标签，确认人口和土地利用指标语义 | 可用于训练和评估的规范数据集 |
| 模型接入 | 训练 XGBoost 适宜性模型并封装预测工具 | 街区适宜性概率、等级和模型版本 |
| 解释分析 | 接入 SHAP 全局与局部解释 | 指标重要性排序和单街区贡献结果 |
| 空间校验 | 接入生态、农田、灾害与边界空间分析工具 | 硬约束冲突清单和空间证据 |
| 效果评价 | 评价准确性、稳定性、工具选择成功率和专家一致性 | 实验结果、问题清单和改进方案 |

近期计划形成三个具体成果：完成真实街区属性的批量导入；完成 XGBoost 预测工具接口；完成一个具有完整输入、预测结果和 SHAP 局部解释的单街区案例。

## 七、结论

本阶段工作以已有论文中的适宜性评价、机器学习预测、可解释分析和规划约束方法为基础，完成了城镇开发边界识别智能体的总体架构设计，并通过对话式 Demo 验证了大模型理解用户意图、自主选择工具和组织结构化结果的基本过程。

该原型为后续接入真实 XGBoost 模型、SHAP 解释和 GIS 空间约束工具提供了稳定的软件骨架。后续研究的重点应从“流程能否运行”转向“模型是否可靠、解释是否合理、空间证据是否充分以及规划专家是否认可”。只有完成真实数据训练、空间约束校验、对比实验和人工复核之后，智能体输出才能进一步作为城镇开发边界调整研究中的辅助决策依据。

本报告所称“已有论文方法”是指项目现阶段已经收集和整理的城镇开发边界适宜性评价、XGBoost 预测、SHAP 解释及规划约束相关研究。后续形成正式学术论文时，应补充完整的文献来源、数据来源、样本规模、模型参数和实验结果。
